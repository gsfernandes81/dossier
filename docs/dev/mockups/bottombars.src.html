Tap the Number

Termux's CTRL and ALT are sticky modifiers: you tap CTRL, it latches, and the next key arrives modified. Not a fragile one-shot — and not a two-finger hold either, which is the better news, because a latch is the one kind of modifier a thumb can work alone. ctrl+x and ctrl+t are two taps. That does not weaken the case for deleting the action bar — it strengthens it, and it takes the pressable chips with it. One verb is left needing a thumb, and the plan already contains the right affordance for it: the header count that told you there were three.

A modifier still needs something to modify, and the only letter source on this phone is the soft keyboard. So the question is not "can a thumb press ctrl+x" — it can — but in which of the two states, and those two states are not what I assumed either.

The keyboard does not cover the screen — the terminal resizes. check it Termux uses Android's adjustResize, so raising the IME delivers a SIGWINCH and the app re-lays out at roughly 45×14 rather than hiding half of itself. Our Msg::Resize already handles it. That makes "IME up" a different layout, not an occlusion — and at 45×14 the floor (38×12) is only two rows away, so it is worth checking with stty size on the device that a taller keyboard cannot push the app below its own minimum mid-query.

Read the two red cells carefully, because they are not equal. ctrl+t is a querying verb by construction measured — app.rs:298 only widens the search into scan text when the query is non-empty, so the toggle does nothing until you are typing, and while you are typing the keyboard is up and ctrl+t works. The correction restores that verb outright in the only state it means anything.

ctrl+x is the residue. "Cold start, show me what is expiring" is a browsing act, done with the keyboard down, and with the keyboard down there is no letter. The workaround is to raise the IME, tap CTRL, tap x, then dismiss the IME again — four or five touches and two re-layouts, to reach the app's most-used filter. One verb, in one state. That is the entire remaining case for a touch control, and it is not a case for three of them.

One test could close even that gap. A sticky modifier latches "until the next key" — and the extra-keys row is full of keys. If tapping CTRL and then ▶ sends ctrl+→, then a modifier tier exists with the keyboard down, built entirely out of the row: ctrl and alt against the four arrows, eight combinations, none of which need a letter. check it

That would make the residue verb bindable — ctrl+↑ or similar for the expiring filter — reachable by thumb while browsing, with no chrome at all. I would still build the header count first: an arrow combination is reachable but not discoverable, and the count is both. But it is the difference between "one verb has no keyboard-down path" and "one verb has no keyboard-down path that anyone would find", which is a much smaller problem.

Worth knowing either way: input.rs matches KeyCode::Right with no modifier guard, so ctrl+→ currently acts as plain →. measured

The recommendation

Delete the action bar. Make the header's expiring count the touch control it was already specified to be. Leave the truth row entirely dim.

H The header count recommended

You tap the number that told you there are three. There is no more discoverable affordance available for "show me the expiring ones", and it costs no rows at all.

It is not a new idea — REWRITE-UI §1 already specifies it ("each count names its : command; on touch, tapping a count jumps there") and it is simply not implemented: taps currently test the search zone, the bar row and the list, and row 0 falls through to Idle. measured

Build it as a toggle, not a jump, so a second tap peels it off and it means exactly what ctrl+x means. Reverse video on the count, because reverse is what this app has decided pressable looks like.

The spare row

Three chrome rows leaves twenty-five for a list that uses twenty-four, so one row is free. It is not a thirteenth document — it is somewhere for flashes, esc again to quit, and the one-shot that teaches the gesture nothing else advertises.

Why not the chips this page recommended last week

Because a state chip cannot be the control. measured — find.rs:349 emits [expiring] only when the filter is already on, so a pressable chip can turn a filter off and the affordance to turn it on does not exist:

Fixing that means always-visible chips carrying a state dot — which is an action bar smuggled into the truth row, with reverse video bleeding into the one row whose texture is meant to be purely informational. The header count has none of that problem.

Where it is tested

The runner-up, and what would promote it

C1 One always-visible chip

A single ^x expiry chip, reversed and anchored bottom-right, showing its state with a dot — the bottom of a portrait screen, where the thumb already is.

This is the fallback, not the pick, and the reason is reach: the header count sits at the top of a portrait phone, which is the far corner for a one-handed grip. The entire design docked search at the bottom for exactly that reason, and putting the one remaining touch verb at the top cuts against it.

That is an empirical question the device answers in two seconds, so it should be answered rather than argued. If the reach is bad, this is what ships instead.

A bug this correction exposed

alt + any letter types that letter into the query. measured — probed against the built binary:

alt+x        -> Char('x')        # types into the query
ctrl+alt+x   -> ToggleExpiring   # identical to ctrl+x
ctrl+alt+z   -> None
alt+Right    -> OpenDetail       # identical to plain Right
alt+Enter    -> Enter

One line causes all of it — input.rs:71 is KeyCode::Char(c) if !ctrl, and ctrl is contains(CONTROL). There is no ALT guard anywhere. Exclude ALT from the printable fall-through whether or not we ever bind an alt verb: on this phone, latching ALT and typing currently pollutes the search.

It also means ctrl+alt+letter is not a distinct namespace — it is aliased onto ctrl+letter. Which is just as well: ctrl+alt is claimed by Termux's own hardware-keyboard shortcuts and by desktop window managers, so it is poisoned for anything primary regardless.

What the freed space is worth: on Find, almost nothing, deliberately. The verb set is complete and the keys are published. The one thing worth reserving is the readline convention users' fingers already know — alt+b, alt+f, alt+d, alt+backspace for word motion and deletion, should the query ever grow a cursor. Where it pays is R4: the detail surface is not search-as-you-type, so bare letters are its primary namespace, and alt+letter becomes the in-edit mirror — s outside a field, alt+s while typing in one. One table, two states, nothing new to memorise. Keep alt verbs non-destructive: on legacy encodings alt is an ESC prefix, and over a laggy link an Esc followed quickly by a letter can arrive as alt+letter. A wrong navigation is recoverable; a wrong delete is not.

Also never bind ctrl+h, ctrl+i, ctrl+m or ctrl+[ as distinct verbs — on the legacy encodings Termux uses they are byte-identical to Backspace, Tab, Enter and Esc. And when R4 wants ctrl+s for save, it should not have it: that is XON/XOFF flow control, and a save key that silently does nothing on some SSH stacks is the worst possible failure.

Optional, and not urged

A second row of macros — [{macro: "CTRL x", display: "exp"}, {macro: "CTRL t", display: "scan"}] — puts both toggles under the thumb in every state. It is global to every Termux session and costs a document row's worth of screen height everywhere, which is a steep price for one verb in one state; and it can send a verb but never show one. If the header count works, nobody needs it.

What I would build

Delete the action bar; implement the tappable header count as a toggle; leave the truth row purely dim. The bar was designed for a thumb with no keys. This thumb has eight, two of them modifiers, and the only verb it cannot reach while browsing is the expiring filter — which already has a better affordance specified than any button: the number that reports it.

Riding along, unconditional: hints shed item by item; the Find chrome goes inert while a record is pushed; the desktop layout gains its missing underline and its missing ^t scans hint; and input.rs stops letting alt+letter type into the query.

Three things to settle on the device before any of it is written into the install notes. Does the CTRL latch reach the row's own arrows? If CTRL then ▶ is ctrl+→, the residue verb becomes bindable with the keyboard down. What is the terminal size with the keyboard up? Expect ~45×14 — if a taller keyboard drops it under twelve rows the app refuses to draw mid-query. And what does long press actually do, now that it is known not to auto-repeat — crossing a long list by thumb was resting on that.
