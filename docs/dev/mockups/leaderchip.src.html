Space Without a Spacebar

Space on an empty query opens the leader sheet. With the phone keyboard down there is no Space to press — and the header count is at the top of a forty-five-row screen, which is both a long reach and not where anyone looks for a menu. So the touch layout needs one chip at the bottom. Five places to put it, all inside the three chrome rows we already have.

Five placements

A Before the prompt recommended

Bottom-left, on the query row, where the prompt used to start. The field keeps thirty-seven typable columns and the ⌨ stays where it is.

The two touch verbs end up at opposite corners — menu left, keyboard right — so a fat thumb cannot confuse them, and the row still reads left-to-right as menu, then type.

B Beside the keyboard chip

Both chips at the right end, where a right thumb rests.

Adjacent targets are the whole problem. Five columns and three columns touching, on the bottom row, both hit by the same thumb from the same angle — this is how you open a menu when you meant to type.

C The far corner

On the truth row instead, hard against the bottom-right corner. The query row is untouched, so the field is at full width.

But the truth row is the second half of the tap-to-type zone, and a chip there is a hole in it. It also sits under the hint text it now crowds, which cost ^t scans its place.

Eleven columns and a word, for a target nobody can miss.

E Replacing ⌨ tempting

One chip, not two: tapping the field already raises the keyboard, so the ⌨ chip is a hint rather than a control.

It is a hint worth keeping. On a first run nothing else says the bottom of the screen is where you type — the underline is quiet and the field is empty. Losing it to save three columns is a bad trade.

A, opened

Two details

QuestionAnswer
Why SPC and not a glyph? It is ASCII, so it cannot render as a box on a font we have not checked — ␣ and ☰ are both unverified on this phone, and a box where a menu button should be is worse than no button. SPC also teaches its own key: the sheet's breadcrumb says SPC, so the chip and the keyboard route are visibly the same thing.
Why not just always show it? A keyboard has a space bar. Drawing a button for a key you are holding is the ⏎ Open mistake, which this whole line of work exists to stop repeating. It appears on the touch layout only — the same test that already decides the two-row search bar.

What I would build

A — the chip before the prompt. It is the only placement that puts the two touch targets at opposite ends of the row, it leaves the hint line intact, and it keeps the ⌨ hint that tells a first-time user where typing happens.

Three touchable things on the whole screen, then: the header count, the SPC chip, and the field. Everything else a thumb needs is on the terminal's own key row.
