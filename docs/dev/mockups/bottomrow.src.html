R-UI · the bottom two rows

The Last Line

The query row sits second from the bottom, with the count and hints under it. Swapping them puts the entry line against the screen edge — which is where every keyboard-driven finder this design has borrowed from already puts it. There is no reason to avoid it, one thing to check on the device, and two small consequences worth naming.

Pane 47×45 browsing · 47×24 typing Changes row order only — no row is gained or lost Tap zones unchanged: both rows still raise the keyboard

The two orders

Why it is the conventional order

Emacs

The minibuffer is the last line of the frame. Nothing is ever drawn beneath it, because there is nothing beneath it.

Vim

: and / take over the final line, below the status line. The status line is what sits above the entry — which is our count-and-hints row exactly.

fzf

Default layout is bottom-up: results, then the info line 4/24, then the prompt on the last row. The layout we would be moving to is fzf's default, and this surface has been called fzf-shaped since §1.

The thumb

The row you touch most — tap to type, tap the chip — becomes the closest to the bottom edge, and the chip takes the corner every phone app puts its primary action in.

What actually changes

Effect
the band Stops being a lit strip with a row under it and becomes a bar docked to the edge. This is the whole point.
the count Moves from directly under the cursor to directly above it. Reading order changes; the distance does not. fzf has always put it there.
messages A flash and esc again to quit now appear above the entry line rather than below. Emacs puts messages on the entry line, which we cannot — either side is a compromise, and above keeps the band clear of text that is not yours.
tap zones Unchanged. Both bottom rows still raise the keyboard, and an overshoot downwards still hits the screen edge.
rows None gained, none lost. Twenty-one documents browsing, ten while typing, exactly as now.
the leader sheet Still opens above the chrome. It now sits above the count row instead of the query row, which puts one more line between the sheet and the thing it filters — no worse.

The one thing to check on the device. check it With the swap, the very last cell of the very last row carries a background colour rather than a plain space. On terminals with automatic margins, writing to the bottom-right cell is the classic way to make the screen scroll by a row. Ratatui draws full-width bottom bars all the time and this is normally handled, but "normally" is not a measurement.

It is unmissable if it happens: the whole screen judders up one line every repaint. If it does, the fix is one column — leave the final cell unpainted, which nobody would ever see.

The states it has to survive

The desktop has the same question

A keyboard layout is query row then hint line. The same swap applies, and the argument is stronger there — a hint line is a status line, and Vim puts the status line above the command line.

What I would build

Swap them, both layouts. I looked for a reason not to and did not find one: no row is gained or lost, no tap zone moves, every state still works, and the resulting layout is what Emacs, Vim and fzf all already do. The band stops floating and becomes a docked bar, which is the thing that prompted the question.

The two costs are real and small. The count reads above the cursor instead of below — fzf's arrangement, so it is well-trodden rather than novel. And messages land above the entry line instead of below; Emacs would put them on it, which we cannot, and above at least keeps the band carrying nothing but your own text.

The one open item is mechanical, not aesthetic: whether painting the bottom-right cell makes the screen scroll. Cheap to see, cheap to fix, and not a reason to hold the change.
