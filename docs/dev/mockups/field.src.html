Marking the Field

The underline sits too high on the phone — through the descenders rather than under them — and nothing in the app can move it: a terminal draws SGR 4 wherever the font's own metric says. So the question is what else can say you can type here. Emacs has two answers, and a third by leaving it out.

Pane 47 columns Constraint underline position is the font's, not ours Rule at stake underline = typable

The mockups were flattering it

Same specimen, twice. On the left as every page in this directory has drawn it; on the right where the font's metric actually puts the line.

That is a mockup lying about the one thing it exists to get right. Every page in this directory that recommended an underlined field drew it with a three-pixel offset — a property no terminal has. The grid machinery was built so a 45-column pane really is 45 columns; nothing was checking that a texture rendered the way the device would render it.

Worth carrying: the mockups are honest about geometry and were never honest about attributes. Colour they hedge correctly — the panes follow the viewer's theme, and every page has a NO_COLOR twin. Underline, reverse and dim have been drawn as they look in a browser.

What Emacs uses instead of a line

WhereHow it is marked
the minibuffer Nothing marks the field. A prompt in minibuffer-prompt face, and the cursor. The prompt names the question, so nothing has to outline where the answer goes.
widget fields
(Custom buffers)		 widget-field is a background face — the field's extent shown as a differently-coloured run, not a rule under it.
and even there The underline `widget-field` grew is contentious enough that theme authors have patched it to follow a border colour instead. A line under a field is a known problem, not a settled idiom.

What shipped

A band across the whole row rather than the field's extent — the row is the field, and a marking that stops where the characters stop is a box drawn around today's text.

DecisionWhy
the whole row The field is the row. Tinting only the span between the prompt and the chip leaves two untinted stubs at the ends, which reads as a bar that failed to reach its own edges.
both ends pinned Background alone is a coin flip on polarity — ANSI 8 is a light grey on a dark theme and near-black on a light one, so a background-only band is unreadable on half of them. Naming the pair keeps §6 intact: the slots are ANSI, so the user's theme still picks the two hues.
one row, not two The row below is the echo area. Two bands would read as a block of chrome rather than as a field with something written under it.
no band under NO_COLOR The first texture on this surface that a monochrome run loses. Acceptable only because the marking sits over words that already say what the row is for — never as the sole signal.

The four that were on the table

A Nothing — the prompt does it recommended

The minibuffer's own answer. Find: in the accent colour, your text at full brightness, everything else on the row dim. The cursor is where you type and the prompt says what typing does.

This only works because the prompt got a name. A bare > with no field marking would be a row of nothing; a named prompt is a question, and a question needs no box around its answer.

It costs the typable texture. That rule was written when the prompt was a marker — the texture was carrying the meaning the words now carry.

B A background over the extent

Emacs's widget-field, in a terminal. It shows the field's full width, which is the one thing the underline did that a prompt does not, and no font metric can put it in the wrong place.

It is a colour. Every other texture here is an attribute, so NO_COLOR loses nothing structural; this would be the first thing on the surface that vanishes. And a tint that reads as subtle against one terminal theme reads as a bar against another — we do not own the palette.

C Underline only what is there

Keep the line, stop drawing it across empty cells. Shown twice again — the second is the phone's rendering.

It does not fix the problem, it shrinks it. The line is still through the descenders of the word you typed, which is the text you most need to read. And the field stops having a visible extent, so it gives up the underline's one advantage while keeping its fault.

D Delimiters

Two dim brackets. No attribute at all, so no font metric can move them, no theme can hide them, and NO_COLOR is untouched. The extent is explicit.

It costs two columns and about fifteen years — a bracketed input reads as a dialog box drawn in text, which is the aesthetic this app has been avoiding everywhere else. Worth keeping in the drawer if A turns out to read as an unmarked row on the device.

What was recommended, and what was chosen

A — drop the underline, and let the named prompt carry it. It is what the minibuffer does, it is immune to the font metric that caused this, and it costs nothing in NO_COLOR. The three textures become two plus the input itself: reverse is pressable, dim is information, and full brightness is what you typed.

That is a smaller vocabulary doing the same work, and it is the one reading that gets more true as the app grows — command mode and the sheet's picker are the same row with a different prompt, and none of them need a box either.

Built instead: B, widened to the whole row. The colour cost is real and is the reason it took an explicit call — but a band cannot be put in the wrong place by a font metric, and that is the fault this page exists to fix. The short underline was rejected outright: it keeps the fault and drops the extent.

Checked against the Emacs Widget manual, wid-edit.el and a Modus themes patch to the widget-field underline.
